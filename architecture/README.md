# Module cycle baseline

`module-cycle-baseline.json` freezes cargo-modules 0.28.0's nontrivial strongly
connected components (SCCs), folded to top-level item-path modules. Each SCC has
`modules` and `edges` fields; edges are `{ "from": module, "to": module }` pairs
inside or entering that SCC. Package keys, SCCs, members, and edges are sorted.
Each package occupies one compact JSON row; empty lists record acyclic packages. The
initial baseline was generated by the real scanner against origin/main at
`b488149774bac3f66828d5b48e7860ab9e5e8447`.

A new SCC, a module joining an SCC, or two SCCs merging fails with the concrete
item-to-item edges. New module edges inside or entering an existing SCC also fail,
even when membership is unchanged. Removing edges, or shrinking, splitting, or
eliminating an SCC fails until the baseline is updated. The bless command in
[AGENTS.md](../AGENTS.md#module-cycle-ratchet)
updates an existing baseline only when there is no growth; it can initialize a
missing baseline. Review baseline reductions alongside the code change.

The check discovers workspace members through `cargo metadata`, selects each
library (including cdylibs) or every binary in bin-only packages, and scans four
targets at a time. It covers default features on the current native target,
without tests, examples, or binaries of library packages. This is a best-effort
resolved-item graph: cargo-modules can miss fully qualified body paths and
`super::` paths, and attributes inherent methods to their type's item path rather
than necessarily to the source file containing the method.

For measurements, `ARCHITECTURE_JOBS=1` selects serial execution. For controlled
checks, `ARCHITECTURE_ROOT` selects a workspace root and `ARCHITECTURE_BASELINE`
selects a baseline file (use absolute paths). Both still use the same metadata,
tool invocation, fold, SCC, and comparison code. For example, this permanent
standalone fixture must fail with a two-module cycle:

```sh
ARCHITECTURE_ROOT="$PWD/crates/workspace-architecture-check/tests/fixtures/planted-cycle" \
ARCHITECTURE_BASELINE="$PWD/crates/workspace-architecture-check/tests/fixtures/planted-cycle/empty-baseline.json" \
cargo nextest run -p workspace-architecture-check --run-ignored only --no-capture
```

The ordinary, tool-free nextest run also checks normal/build dependency adjacency
for `collaboration-contracts`, `collaboration-runtime`, `collaboration-application`,
and `codex-router-host`, in that order from lowest to highest layer. The small
table in [crate_layers.rs](../crates/workspace-architecture-check/tests/crate_layers.rs)
allows lower layers and rejects upward edges.
Only present workspace packages are checked; dev edges are reported separately
and allowed. Synthetic metadata covers upward normal/build rejection, downward
edges, mixed build/dev dependencies, and missing packages.
