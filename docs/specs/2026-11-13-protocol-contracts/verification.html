Verification Design

Verification is built first, in D0, and checks four things:

  • Edges: every message is checked against its own definition.
  • Nodes: every conversion is checked at its edges, with its state and reverse paths.
  • Streams: each of your actions runs end to end on the real Codex CLI, once against real Codex (the reference) and once against our Router with Claude or Cursor behind it. The two runs must match.
  • Baseline: today's bugs must fail in the harness before anyone fixes them.

The four layers

Typed TypeScript in verification. Where a check is easier to write in TypeScript (stream comparisons, screen and event readback, sample generation), the drivers import types rather than hand-writing shapes. Router vocabulary types (session events, approvals, commands) come from Rust through Specta. Codex types come from the TypeScript that Codex itself exports at the pinned release. A driver that reads a message the wrong way then fails tsc, just as Rust fails the build. The package's existing runner (node --test) stays (D26).

The observations

O1 · Wrong code does not compile

Uses the workspace's existing trybuild dependency. Fails a wrong build: an API that still accepts raw JSON lets the snippet compile. Decides R1, R3, and the build side of R9. For ACP enums, which the compiler can't make exhaustive, a separate required check compares every variant in the pinned SDK schema with each node's disposition table (D25). Fails a wrong build: an SDK bump that adds a variant with no entry.

O2 · Edge conformance

The samples come from the export itself, not from our generator, so a generator that drops a field or closes an open enum fails here. The same tool runs each override's test. Built in D1. Each edge type has its own independent reference:

  • Codex edges: the pinned Codex export.
  • ACP edges: the ACP JSON schema for the version the pinned SDK targets, kept as a test fixture only. Samples from it are decoded and re-encoded with the SDK types.
  • Router vocabulary edges that cross languages (N12's metadata, and the TypeScript drivers): TypeScript serializes a sample with the Specta types, Rust decodes and re-encodes it, and TypeScript decodes it again. The values must be equal, including Claude's reasoning choices and default.

Decides R1, R2, R4, R5, R6 and R22.

O3 · Refresh and drift

Decides R7. The online check against a pinned, installed Codex depends on A23.

O4 · Node taps

A harness drives one node in-process. It feeds every input variant from the conversion catalog into the node's inbound edges and records what comes out, plus the state before and after. It covers every node except N2, the opaque relay:

  • N1, N3, N4, N6, N7, N8, N9, N10;
  • N5's fan-out: each event reaches every subscriber (N3, N11's events_observe, inventory, and N4's turn wait);
  • N11's routing: each tool call reaches its command, carrier or native-control target;
  • N12, whose TypeScript output is decoded by the real Rust decoder.

It also checks:

  • approvals in both directions, including that the chosen option reaches the provider;
  • malformed Codex replies, which must give OutcomeUnknown or Protocol and retire the connection;
  • whether N9 has a real client (D24).

Decides R12, R13, R17, R20, R21, R23, and the runtime side of R9. Built in D0. Each node's cases are added in the deliverable that fixes that node.

O5 · Streams: Codex compared with the Router

Extends the existing Codex ACP journey driver (capture-run.ts --codex-acp-only), which already reads the wterm grid and the session record. It runs against the debug Router only, with Claude on Haiku.

Fails a wrong build: a steer with no receipt, 770K shown for a 1M window, a lost model change, or an approval whose choice never reaches the agent.

Decides R10, R11, R24, and R2 through /model. Also decides R8 once Q1 is answered. Lifetime: lasting; it reruns on every Codex refresh.

What "match" means: Claude and Cursor answer differently from Codex: different text, a different number of message chunks and items, and their own reasoning and tool items. So text and exact sequences are never compared. Each run is reduced to a turn skeleton and checked against the rules below.

Proposed by the D0 Implementer, adopted by the Lead on 2026-11-14. D0 builds these rules with negative controls; D3 runs them live.

Why this is independent of today's code: the rules are checked against the real Codex run first. If real Codex breaks a rule, the rule is wrong, and the Verifier reports it to the Lead instead of relaxing it.

Usage and context window: compared with what the provider itself reported in that turn, not with Codex's numbers. The route: N6 stores the provider's ACP usage_update payload unchanged as the turn's Usage item (provider_item_projection.rs:281-284), so the driver reads that item from the debug Router's session record. Its size must equal the context window the CLI receives and shows, and its used must equal the used tokens. A build that shows 770K when the provider reports 1M, or any window other than the reported one, fails. Limit: the payload passes through the ACP SDK's types, so a field the SDK does not know is not compared; size and used are SDK fields.

Cursor journeys need the verification skill's Cursor qualification first. Until then, the Cursor rows are planned but unqualified. Depends on it: O5 and the D2–D4 Cursor checks.

The existing journey driver can be extended to run a second target (real Codex) and compare the two runs without a new harness. The D0 Verifier read its source on 2026-11-14: it pins Codex 0.165, drives only Claude or Cursor sessions, reads only the model from the footer, and its reply check accepts swapped order, a missing client id and a changed window. So D0 extends it with a real-Codex target, the 0.166.0 pin, usage reading and the k1–k5 rules; if that needs more than an extension, the plan's stop condition applies. Depends on it: O5.

O6 · Baseline

There are two kinds of evidence. Historical regressions show the checks can detect a bug: they fail on the commit before the fix and pass on the head. Current defects fail on the head until their deliverable lands. Decides R25. Capturing the baseline happens once; the checks it seeds stay as lasting regression tests.

Only defects visible on the wire belong in the runtime baseline. Untyped steering sends the same bytes as typed steering, so no runtime check can see it. It is a type-level defect, decided by O1 (a compile-fail case) and the O7 review in D3, not by O4 or O5.

O7 · Structure, per deliverable

A one-time review for each deliverable, not a permanent scan of the repo. The exception is the tool-schema equality check, which stays as a focused test. Decides C1, R14, R15, R16, R18, R19 and R26.

Every edge, node and stream, and what decides it

R21 is checked per message, not per protocol family. Each node's conversion catalog is one exhaustive table in code, keyed by input variant, and each row names the output kinds it may emit. O4 feeds every input variant in the catalog, so no catalog row goes unexercised. For each variant it records the messages the node actually produced and consumed, and compares them with that row and with the producer/consumer table. A node path that is not in its catalog cannot compile, for our own types, or fails the D25 check, for ACP. Paths that are not node conversions at all, such as code outside the twelve nodes that sends a message directly, are found by D0's review of every send site on each edge. For S6, the Codex parts of each advertised tool schema are compared with the pinned export, an independent reference, not only with the type that produced them. For S7, the reasoning choices and default the Claude wrapper produced must equal the values the Router decoded.
