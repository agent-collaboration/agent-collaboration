Sessions on other machines

From any machine, you or an agent can create a session on another machine. You pick its endpoint, model, effort, access, folder and an optional first message, and get back the new session's address. It travels through central on the same safe path as automations: held if the other machine is off, never lost, and never created twice. Today that's refused with "conversation endpoint belongs to another service".

How it works

Who creates, who approves

  • The creator is really you, or your session on machine A. Central checks that the request came from that machine, and refuses a mismatch. The new session shows its creator as "you on A" or "that session on A".
  • Permission prompts go to you, the owner, by default. Sending them to an agent on another machine needs cross-machine approvals, which aren't built yet, so that choice is refused for now.
  • Machine B decides first. Its existing checks run before anything is created: the endpoint and its models, the access level and the folder. There's no new allowlist.

When a remote create names no approver, the target machine's Chief of Staff session approves; you name it once per machine. A machine with none named refuses before creating anything. This is a named interim step: it ends when routed approvals land, a separate later design in which the requester becomes the default.

What you get back: two parts

PartPossible answers
The sessioncreated (its address, with settings fully or partly applied), refused (B's reason), or unknown
The first messagenone, accepted, failed (reason), or unknown
  • Nothing is hidden or doubled: a created session is always reported, even if the first message failed. It's never created twice, and a message is never resent blindly.
  • Waiting: if B is off or slow, you get pending with the operation ID. Stopping the wait cancels nothing, and operation show or wait gives the result later.
  • Retry with the same operation ID gets the same answer. An old-release B is refused as targetNeedsUpgrade.
  • After a crash, B checks its existing create record rather than creating again.

Central already needs to hand work to a specific machine, safely, for automations. A session create is one more kind of work item on that path. A fresh-each-run schedule already does the same thing on a timer, and this does it right away.
