Firing and mail

Central keeps the clock, on a 5-minute grid. When grid point 10:05 arrives, central records every firing due then, groups them by machine, freezes one batch per machine, and tells each machine it's ready, right away. Central keeps the batch until the machine confirms it has it. The "ready" notice is only a wake-up on central's existing per-machine notice channel. Whenever the machine connects or gets a notice, it asks central for every batch it hasn't confirmed, fetches them, stores them locally, then confirms. Agent-to-agent messages keep using the mailbox as today. The machine that created the automation doesn't need to be on.

"A with send time batching" (you, 31 Oct). Central fires at the due time, and firings for one machine travel together. Nothing waits on the machine for later, and cancels happen only in central.

One grid point, end to end

Few, larger messages: following Cloudflare's WebSocket guidance, the machine packs many items into each frame, so a pull, a confirm or a report call carries many items, instead of one call per item. Every arrow is a call central already allows, in its one-way order. If B is off for a week or more and its notices have aged out, nothing is lost: on reconnect it asks for its unconfirmed batches, and central still has them.

Every arrow is an object-to-object call central already allows, in its one-way order. Nothing new is added to the call graph.

The grid

  • Every due time rounds up to the next 5-minute mark of UTC time, so nothing fires early. A time already on the mark stays.
  • Several times that round to the same mark make one firing. A cron entry every minute fires once per 5 minutes.
  • Time zones and daylight saving still decide the nominal time; the rounding happens after.
  • An interval schedule must be 5 minutes or longer. A wake repeats every 10 minutes or slower.

Pause, cancel and change: central only

  • The cutoff is central's commit that freezes a firing into a batch.
  • Before the cutoff: a pause, cancel or change takes effect, and that firing is never sent, or is sent with the change.
  • After the cutoff: the firing is out. Your command's answer says alreadySent, and nothing chases it to the machine.
  • If central can't tell whether the "ready" notice was appended, the firing shows unknown until central checks the machine's notice position. It's never announced twice.

Firing states

Reports from the machine carry a sequence number, stored on the machine together with each state change, so a restart continues it. Central applies them in order, ignores repeats and older ones, and never moves a finished firing back.

How the clock works (Cloudflare and Tokio)

There's no polling loop. Central's Fleet object holds one alarm, set to the next due time. When it fires, the alarm handler runs one step: send everything whose rounded time has arrived, then set the alarm for the next due time. Creating or changing an automation moves the alarm earlier if needed, in the same transaction. The alarm is shared with central's other Fleet work through AlarmOwner, which keeps only the earliest. Alarms can arrive more than once, so the step is safe to repeat. On self-hosted Tokio, the same thing is a timer.

It's a scheduler, the way Cloudflare describes it: stored events plus one alarm, like setTimeout for a Durable Object. The automation schedule lives in central's table, and the alarm handler processes everything due, then sets itself for the next. On self-hosted Tokio, the same interface is a real timer.

Cloudflare retries a failed alarm up to 6 times, then gives up. If that ever happened, every automation would stop. So:

  • a broken definition is reported on that automation and never stops the others;
  • a temporary failure (storage, platform) changes nothing, so every owed firing stays owed and goes out on the retry;
  • after each successful pass the handler sets the next alarm;
  • every request to central (create, list, a machine pulling) checks the alarm is set for the earliest pending time, and restores it if needed. Overdue firings are then sent once.

Between due times nothing runs: there are no ticks and no retries standing in for a timer. The notice journal runs on its own alarm, so one batch is a few object events, not one. The cost page keeps that as a planning model until it's measured.
