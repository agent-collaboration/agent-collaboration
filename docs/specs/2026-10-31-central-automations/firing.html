Firing and mail

Central keeps the clock. When an automation is due, central records one firing and sends it as an ordinary message. It uses the same outbox → central ledger → inbox path as every other message, with central itself as the sender. The machine that created the automation doesn't need to be on.

One firing, end to end

How the clock works (Cloudflare and Tokio)

There's no polling loop. The Fleet object holds one alarm, kept at the earliest due time; a request for a later one leaves it unchanged (AlarmOwner, runtime-primitives/src/alarm_owner.rs). Between alarms, Cloudflare may evict the object from memory, and it re-creates it when the alarm fires.

On self-hosted Tokio, the same wake request is a Tokio timer. Messages to machines go over each machine's one hibernatable WebSocket: it stays open while the object sleeps, a hint wakes the machine, and the machine pulls its mail. When a machine is offline, its mail waits in central's mailbox until it reconnects.

The message

PartValue
SenderAutomation { automation_id }. A new sender kind beside session, human user and project.
BodyFiring { firing_id, automation_id, revision, due_at, valid_until, payload }. The payload is either a wake (its message and creator) or a schedule run (instruction, destination, model, effort, timeout).
RecipientThe target session, or, for a fresh-each-run schedule, the machine endpoint. That's a new recipient kind, because no session exists yet.
Valid untilA wake's end, or a schedule's next due time, because the next firing replaces it.

Repeats and overlaps, kept as today

  • While a wake's firing is still undelivered, new due times fold into it instead of piling up.
  • A schedule has at most one running and one waiting run; extra due times fold into the waiting one.
  • The next due time is computed from now, so a long outage doesn't produce a burst.

Edits, cancels and unknowns

  • A change acknowledged before a due time decides that firing. A firing already admitted keeps the revision it was admitted with.
  • A pause or cancel reaching a firing that hasn't been delivered stops it with the existing mail cancel, and it ends as cancelled.
  • If central doesn't know whether a send landed, it reconciles through the mail status. It never sends again under a new identity.
  • States only move forward, so a late report from the machine is answered as stale and ignored.
  • Central restarts mid-alarm: the durable step resumes; the firing and its send obligation were one transaction, so nothing is admitted twice.
  • Target machine off for days: the item is held, then delivered, or expired by its valid-until.
  • Central unreachable: nothing fires until it's back. Under U80 a machine only works online, so this matches.
