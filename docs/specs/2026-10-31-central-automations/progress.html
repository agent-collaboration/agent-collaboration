Five of those decisions explained

You asked about these five. Each one says what problem it solves, what was decided, and where it's written. The Program Design (program-design.md) and the Specification (specification.md) are in this folder.

The alarm budget is fixed, not raised

The problem. Each organization's central Fleet has an alarm, a timer that wakes the Fleet to do scheduled work. An existing test, bounded_gate_reads, says a freshly created, empty Fleet's alarm may run at most 2 SQL statements. It's there so central stays cheap per organization, because on Cloudflare every query costs. PR 2's automation clock added 5 statements that ran on every alarm: a catalog scan, an occupant check, the deadline query twice, and a Batch-retention delete. So an empty Fleet ran 7.

What was decided. Not raising the test to 7, which you've ruled out. Instead, the alarm's existing first read also asks one cheap question: is there any Automation, timing row, Firing, shared Batch or remote-create work item at all? If not, the automation phase is skipped, so the count is back to 2. If there's anything, the automation phase runs exactly as before, which is why nothing owed can be hidden. The Verifier confirmed it: the alarm went from 8 statements before the fix to 2 after it.

Where. Program Design line 32, the timing row: "An empty Fleet skips automation work". The code is commit a2c20aba2, with the test crates/collaboration-service/tests/fresh_fleet_alarm_budget.rs.

The interim approver lives in a read-only remote-create.json

The problem. When someone on machine A creates a session on machine B (R16), the new session needs an approver: who answers its permission prompts. You decided the requester will be the approver later, in PR 3, once approvals route through central. For now, if no approver is named, it's B's Chief of Staff session, named per machine. So each machine needs a setting that says which session is its Chief. That setting had nowhere to live, because the Router's host configuration is built in code.

What was decided. One single-purpose file in the Router's root folder, remote-create.json, containing { "defaultApprover": <session address> }. You edit it by hand on each machine, the same way as ports.json. It's read once at startup.

  • No file means no default: a remote create that names no approver is refused (approverRequired) before anything is created.
  • A malformed file stops the Router from starting, rather than guessing.
  • Agents never write it.
  • It's marked interim and is deleted when PR 3 lands.

What you'll need to do. Once this ships, create that file on each machine, naming that machine's Chief of Staff session.

Where. Program Design line 84, "Interim approver setting home". The requirement is Specification R16 (lines 142–152), and the check is V18.

"Carried" work at the handover, and why central's alarm wakes for a carried Run

The background. When a machine upgrades, it moves its local Schedules and Wakes to central once (R11). At that moment some work may already be under way locally. That's carried work, and it must happen exactly once, never twice and never zero times (R12):

  • A carried waiting Run is a Schedule run already queued locally but not started.
  • A carried Wake is a Wake delivery already admitted locally, and being delivered into a session.

Why the Router gives a carried Wake its Firing ID. The delivery is already happening on the machine, so it finishes there. Central still has to know about it, or it would think that occurrence is still owed and send it again: a double delivery. So in the freeze transaction, the Router assigns that delivery a Firing ID and puts the ID in the frozen payload. Central records the Firing as already received by that machine and never puts it in a Batch. When the delivery finishes, the machine reports the outcome under that same ID. The ID has to exist before the import, inside the frozen bytes, so that every retry carries the same one.

Why central's alarm wakes for a carried Run. A waiting Run's due time gets fitted to the 5-minute grid. If it was due at 10:02 and the move happens at 10:03, it's now owed at 10:05: in the future. Central's alarm used to wake only for each Automation's next due time and for Wake expiries. If that Schedule arrived suspended, say a cron that can't be rewritten exactly, it has no next due time. Then nothing would wake central at 10:05, and the owed Run would never fire. So the alarm's wake-up time now also includes the due time of a still-pending carried Run. At that time the Run is released once from its saved entry, and the suspended Schedule fires nothing else until you fix it.

Where.

  • Program Design line 79, "Handover import contract": the carried_firing field and its handling.
  • Line 80, "Handover Router storage": where the machine records it.
  • Line 32, the timing row: the clock's wake-up rule, "minimum of three sets".
  • Line 86: a suspended move with a carried waiting Run.
  • The rules come from Specification R11 and R12 (lines 110–135), and the check is V14 (line 202).
The handover payload travels as the exact frozen bytes, and central computes the digest itself

The problem. When a machine moves its definitions to central, it freezes each one: the converted timing, the watermark (what already ran locally), and any carried work. Then it sends the result to central. If the answer gets lost or the machine crashes, it retries. A retry must never create a second copy, and it must never send different content under the same name.

What was decided.

  • Freeze once, store the bytes. The machine writes the frozen payload to automation_handover.frozen_payload, and every send, retries included, uses those exact stored bytes.
  • Central checks for itself. Central computes a SHA-256 fingerprint of the bytes it receives, and never trusts one the sender supplies.
    • Same machine, same Automation and same fingerprint: the answer is "already imported", with nothing written twice.
    • A different fingerprint: the answer is "import conflict", before anything is written.
  • Sent as a string. The payload travels as a JSON string inside the request. Central's request decoder would otherwise reorder keys and change the bytes, which would break that fingerprint check.

Where. Program Design line 79, "Handover import contract", under "Bytes and digest". The rule that every retry sends the same bytes is in Specification R11 (line 123).
