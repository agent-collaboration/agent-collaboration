The central list

Every schedule and wake lives once, on central, in the Fleet face. The Fleet face already owns central's own state, runs the same on Cloudflare and on self-hosted Tokio, and wakes itself on alarms. Any machine's Router reads and changes the list through calls on the machine session it already holds. No machine keeps its own copy.

The same wake … and schedule … commands, with the same output. The target can now be a session on any machine, and the list is the same wherever you ask.

Where it lives

What central stores

  • The definition is kept whole: a schedule keeps its instruction, timing, destination (an existing session, or a fresh session in a folder), model, effort and timeout; a wake keeps its target, due time, repeat and creator.
  • Every ID is UUIDv7, and kinds and states are checked by Rust types, not by database CHECK rules.
  • Finished firings are removed after 2 months, the same retention as PR 1.

Rules, checked once against the whole list

RuleWhat happens
No projectAn automation has no project, so a lease never pauses or delays it.
Wake limitsOne-shot wakes at most 24 h ahead; repeating wakes end within 7 days, at most every 5 min. A violation is refused with its limit named.
One active wake per sessionChecked across all machines now. A second one is refused as wakeExists, naming who set the first.
Changes carry a revisionChange, pause, resume and cancel send the revision they saw. A stale one is refused as revisionMismatch, so two people editing can't overwrite each other silently.
Writes need centralIf central can't be reached, a write is refused as centralUnreachable. Nothing is queued to apply later. A read shows the last list with its "as of" time, or fails visibly.
Calls the Routers make
  • AutomationCreate, Change, Pause, Resume, Cancel, List, Show
  • AutomationImport: the one-time move from a machine (see Moving to central)
  • FiringReport: the receiving machine reporting what happened (see On the receiving machine)
