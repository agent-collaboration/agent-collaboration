The central list

Every schedule and wake lives once, on central, in the Fleet face. The Fleet face already owns central's own state, runs the same on Cloudflare and on self-hosted Tokio, and wakes itself on alarms. Any machine's Router reads and changes the list through calls on the machine session it already holds. No machine keeps its own copy.

The same wake … and schedule … commands, with the same output plus clearer answers (alreadySent, outcomeUnknown). The target can now be a session on any machine, and the list is the same wherever you ask. Instructions move to central too, so a schedule can run on a machine that never stored its instruction.

Where it lives

What central stores

  • The definition is kept whole: a schedule keeps its instruction, timing, destination (an existing session, or a fresh session in a folder), model, effort and timeout; a wake keeps its target, due time, repeat and creator.
  • Every ID is UUIDv7, and kinds and states are checked by Rust types, not by database CHECK rules.
  • Finished firings are removed after 2 months, the same retention as PR 1.

Rules, checked once against the whole list

RuleWhat happens
No projectAn automation has no project, so a lease never pauses or delays it.
Wake timingOne-shot wakes at most 24 h ahead. Repeating wakes end within 7 days and repeat every 10 minutes or slower. Everything lands on the 5-minute grid.
Wake slotA session's slot is held by an active or paused wake. Replacing it needs replace, and only the wake's creator, the target session or you may do it; anyone else is refused as wakeExists, naming the creator. A replacement is one atomic step.
Changes carry a revisionA stale revision is refused as revisionMismatch.
Safe retriesEvery command carries an operation ID. A retry returns the original result; the same ID with different content is refused as operationConflict.
Writes need centralCan't reach central before sending: a definite centralUnreachable, and nothing is queued. Sent but no answer: outcomeUnknown with the operation ID, never "not applied"; retry with that ID to get the real result.
Cancel in central onlyOnly firings not yet sent are affected. After the cutoff the answer says alreadySent.

The limits are part of the contract

Every limit is defined once, in one limits module:

LimitValue
grid step5 min
wake minimum period10 min
one-shot wake, how far ahead24 h
repeating wake lifetime7 days
schedule minimum interval5 min
notification interval10 min
notification listing50 entries
batch100 entries
instruction text, wake message1 MiB (today's limits)
identity fieldstoday's limits

From there it goes:

  • into the published schema, with minimum, maximum, step and a plain description;
  • into every check: the CLI, MCP and central calls, and when a stored row is read back. A violation is refused as limitExceeded, with the limit's name, your value and what's allowed. There are no SQL CHECK rules; typed Rust constructors do it;
  • into the MCP tool schemas and CLI help, so an agent knows the limits before it calls.

A test walks the whole list and checks that the schema and the real acceptance agree.

Calls the Routers make
  • AutomationCreate, Change, Pause, Resume, Cancel, List, Show, plus instruction create and update. Each carries an operation ID.
  • AutomationImport: the one-time move from a machine (see Moving to central).
  • FiringReport: the receiving machine reporting, with a sequence number (see On the receiving machine).

The calls ride each machine's existing session to central. Today's refusal "endpoint belongs to another service" goes, and the old remote-wake request path is retired.
