Central automations

What broke: you meant automations to be definitions of scheduled messages, kept in one central place for every machine. That was never built. Each machine keeps its own schedules and wakes in its own automation.sqlite, fires them itself, and nothing about them is on central.

Why nobody caught it: the board design that holds your later decisions sits on a local branch, design/board-orchestration, 667 commits ahead of main and never published. On 25 Oct, #160 copied an older version of the requirements onto main. Agents read main, so they read rules you had already removed.

What we're doing: one stack of two PRs that merge together.

  • PR 1 (fix/router-db-retention): retention, vacuum and WAL.
  • PR 2 (design/automations-central): this design, then its implementation and migrations, plus a safe republish of the board design.

Recommended by the Lead and by the Advisor, and taken as the working decision: central decides when an automation is due and fires it. A machine that's asleep or off doesn't stop it.

It comes from your words "cross system in a central location" (31 Oct) and "should always work" (19 Oct). It also closes the timer-location question that was left open on 4 Oct (D2).

If you meant central to hold only the definitions while a machine keeps the timer, say so and this changes.

Today versus the design

Today (main)

The list exists only on the machine that made it. If A is off, nothing fires.

The design

One list, the same from every machine. Firing is a message on your outbox → central → inbox path.

How it went wrong

From the Advisor's read of this Mac's transcripts, ledgers and git. Sunclaw's records are still being searched.

You asked where automations live

"what about automation? is that a global thing? is that a local thing? … where they live?" The Lead proposed definitions "global: on the fabric … one owner, one clock", but left the timer location open (D2). It was never closed, and the automation lane (P4) was never built.

A Lead added "a project's wakes and schedules pause" to your lease rule

Your words were about 4-hour leases. The pause clause was the Lead's own, marked as authorized. The same Lead admitted it on 18–19 Oct.

You asked "did we not put wakes and automations in central not in a project?" and removed the project link

The Advisor answered yes, wrongly adding that a project controls firing. You said automation "should not be associated with anything, should always work". Commit b8e63fedf (U80) recorded it on the local design branch only.

The published copy was the old one

On 22 Oct a reviewer noticed the docs in the published tree were "an older copy", and it wasn't fixed. On 25 Oct, #160 put exactly the pre-U80 requirements onto main, where they still are.

Only the cross-machine wake slice was built

Remote wake creation and controls (the B3r slice) shipped. They give each target machine its own timer, not a central list.

Much of the code already follows your later decisions: central-first project creation, no offline writes, and the removed lost-write family. It's the published documents that contradict it. So the docs fix is mostly about the documents, not about code.
