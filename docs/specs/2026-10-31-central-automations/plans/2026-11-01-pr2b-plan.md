# PR 2b: typed interactions get their own crate

Owner, 2026-11-01: "shouldn't interactions be its own crate?", then "then do pr 2b for mechanical split". PR 2b is a mechanical move with no behavior change, stacked on PR 2. PR 1 and PR 2 move no crates.

## What PR 2b is

`interaction.sqlite` holds two different things in one crate today: the typed interactions (approval and question history, settled answers, approval routes) and the delivery machinery (pushes, mail, retries, subscription progress). PR 2b gives the typed interactions their own crate and leaves delivery where it is.

| | `interaction-storage` (stays) | `interaction-history` (new, layer L3 storage) |
| --- | --- | --- |
| Owns | `InteractionStore`, the only opener of `interaction.sqlite` (connect, pragmas, schema inspection, WAL); the one migration set for every table; `StorageError`; pushes, mail, retries, held mail, subscription progress, notification windows (M6), push retention | `InteractionHistoryRecord` and its states, codec, store and decode; question history; settled answers; `StoredApprovalRoute` and its queries; route pruning; their tests and `.sqlx` query files |
| Depends on | nothing in the other crate | `interaction-storage`, borrowing `InteractionStore`'s transaction connection, the pattern `interaction_store.rs` already documents |

## Fixed rules

1. **One database, one migration set, one file owner.** Every migration, including `202610310001_settled_answers.sql` and `202610310002_approval_routes.sql`, stays in `crates/interaction-storage/migrations/`. No migration is added, renamed or edited. No stored data moves, and `_sqlx_migrations` is unchanged.
2. **One direction:** `interaction-history` → `interaction-storage`, never back. No trait, callback or feature flag is added to get around a reverse edge.
3. **Hard cutover:** consumers import from the new crate. `interaction-storage` re-exports none of the moved types.
4. **No behavior change:** no logic edits, no new public types, no renamed types. Two renames are allowed: the moved crate path, and `initialize_history`, which actually opens the whole database, so it moves into `interaction_store.rs` as `open_interaction_database`.
5. **Moves keep history:** use `git mv`, then fix imports, so each file's history follows it.
6. **The ratchet may not grow.** The crate graph stays a DAG. Run the module-cycle ratchet root-qualified, in the worktree's own target. Bless it only when the graph shrinks.

## The two reverse edges, and how each is cut

| Edge today | Cut |
| --- | --- |
| `InteractionStore::open` calls `interaction_history::…::initialize_history` (`interaction_store.rs:38`) | the opener moves into `interaction_store.rs`; history code receives an open `InteractionStore` |
| `interaction_retention.rs:49` calls `approval_routes::prune_expired` | **Lead's decision:** retention stays with the file owner. The pass runs every prune in one `BEGIN IMMEDIATE` transaction under one cutoff, `INTERACTION_RETENTION_MONTHS` (`interaction_retention.rs:35-41`), so the route-prune `DELETE` moves into `interaction_retention.rs` and stays in that transaction. Route writes and reads move to `interaction-history`. One pass, one transaction, one cutoff, and no new seam |

Anchors are at PR 1's head `3b48541ff`; the worker's placement fix may shift line numbers.

Any other edge that step 0 finds gets the same treatment: it is listed, its cut is proposed, and nothing moves until the Lead approves.
