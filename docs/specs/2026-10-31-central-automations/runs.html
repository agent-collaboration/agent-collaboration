On the receiving machine

The machine that gets a batch does what it does today for each entry. A wake becomes the same ⏰ Router wake push in its session. A schedule run starts in its bound session, or in a fresh session in its folder, with the instruction version central froze, the schedule's model, effort and timeout, and the same continuity and summary as today. What's new: it gets its entries from central's batches instead of its own timer, it can never lose or double one, and it reports back.

From inbox to session

The receipt and the work it owns are written together. If the machine crashes right after, the work is already queued, and today's drivers pick it up on restart with their existing recovery. A redelivered batch finds the receipt and leaves the existing work running. A crash after the session accepted the input but before the outcome was saved is handled the way it is today: reconciled, never blindly repeated.

Schedule runs

  • The instruction is frozen when central admits the firing. The batch carries a reference to that exact version, and the machine fetches its text from central once. A later edit doesn't change a run already admitted, and the creating machine can be off.
  • Central holds the waiting run. It sends a schedule entry only when that schedule has nothing running, so the machine starts it straight away, with its frozen inputs, at the same point today's runs start.
  • A local copy of each definition is kept read-only, so the machine's run and delivery records keep pointing at a real row. The local timer never runs these copies.
  • Continuity (the previous run's summary as context) comes from the previous completed run of that schedule on this machine, which is where its destination is.
  • The run driver stays. Only the local timer's job of deciding when things are due goes away; preparation, execution, stop and summary are driven exactly as today.
