Your decisions

Seven decisions are open. Five are about what a Router saves on its own disk, in its two local databases: automation.sqlite (automations) and interaction.sqlite (messages and approvals). I built all five my recommended way so PR 2 could keep moving. Each lives in one migration and one place in the code, so if you choose differently it comes out before release. They only need your answer before PR 2 merges. The last two are housekeeping on Sunclaw. For the overall status, see Where the work stands.

Where these decisions sit

Two machines, one central. Machine A is where you, or an agent, act; machine B is where the work runs. Central holds the shared list of automations and hands work to each machine. Each number below is one decision on this page.

Decisions 6 and 7 are about Sunclaw itself, not product design.

1. Prepare retry: how B safely retries after losing central's answer

The decision: when B has created a Schedule's thread but lost central's reply, how does B retry without making a mess?

Background. Some Schedules run every time in the same long-lived Codex thread. Before one can be switched on, schedule prepare has to create that thread on the machine where it will run, then tell central which thread it is. That second step is called "binding". Program Design line 73, "Schedule prepare".

Why it's open. Today B saves nothing it could resend. To retry safely, it needs the exact request it sent the first time, including "revision 7", because the Schedule could have been edited in the meantime. No earlier decision of yours covers this.

What changes

One new, usually-empty column, central_bind_request_json, on an existing table in automation.sqlite. That table, operation_receipts, already holds one row per operation so it can be replayed. The request goes into it before it's sent.

On retry

B resends exactly the same bytes. Central sees the same operation and returns its original answer. The thread is never created twice.

Gains

A simple, exact replay. It's the same "same request, same answer" rule the rest of the system uses.

Costs

One column in a migration. Old rows stay empty.

What changes

Nothing new is saved.

On retry

B reads the Schedule from central. If it's already bound to thread T, B is done. If it's still unprepared, B binds again under a new operation. If it changed, B reports a conflict.

Gains

No database change.

Costs

More logic, with more cases to get wrong, such as an edit landing in between. The "same request, same answer" guarantee is lost.

Who weighed in. The Router lane (lane 2) found the gap and proposed A. I agree.

Recommendation: A. It's the smallest change that keeps "only central's real answer finishes the operation".

If you wait. Nothing is blocked: A is built. You need to answer before PR 2 merges.

Background for decisions 2–4: the move to central

When a machine first starts the new release, it moves each of its local Schedules and Wakes to central, once (Specification R11, line 110), and every Schedule or Wake has exactly one owner at every moment (R12, line 125). The machine "freezes" its local copy, sends it to central, and marks it "moved" once central confirms. Some work may be half-done at that moment: a Run waiting to start, or a Wake message being delivered. That's called carried work, and it has to happen exactly once. Program Design flow 5, line 100, and the rows at lines 78–80.

2. What happens to a Run that was waiting when its Schedule moves

The decision: on the machine, how does a waiting local Run end once central has taken over?

Background. A Run was queued locally but hadn't started. Central now owns that occurrence and will run it once, at its fitted time. The local Run row must stop counting as waiting, without pretending it ran or failed for some other reason. The local Run states today: preparing, then executing, then finished or failed. There's no "cancelled" state, and the failure path only accepts preparing Runs.

What changes

The Run ends in today's "failed before it started" state, with a new reason value, transferredToCentral, saved in an existing field.

Gains

The row and its history are kept, and the reason says exactly what happened. There's no new state.

Costs

One new value stored in an existing field.

What changes

The waiting Run row is removed.

Gains

Nothing new is stored.

Costs

History disappears, and you can't see afterwards what was handed over.

What changes

A new Run state that every reader and listing has to learn.

Gains

The most explicit option.

Costs

A wider change across every place that shows Runs.

Who weighed in. The central lane (lane 1) proposed A. I agree.

Recommendation: A. If you wait: nothing is blocked. Where: Program Design line 80, "Handover Router storage", point (1).

3. What the machine remembers about the move

The decision: where does the machine save the few facts it needs to make the move safe to retry, and to report on it?

Background. To retry an interrupted move and report on it afterwards, the machine has to remember three things:

  • the import ID it used, so a retry reuses it;
  • the final result of any carried Run, to resend it if that answer is lost;
  • for the move report you'll see, whether each item's timing was adjusted and whether a Wake ended.

The report counts can't be worked out later. Once a definition is converted, its original timing is gone. The spec requires that report (R11, line 110). The frozen copy itself is already saved in automation_handover.

What changes

New typed operation kinds in the existing operation_receipts table, which already holds per-operation replay records. There's no new table or column.

Gains

It reuses the existing replay machinery. The frozen copy stays the only copy of the definition.

Costs

New stored kinds in an existing table.

What changes

A separate table just for move bookkeeping.

Gains

Kept apart from the operation table.

Costs

A second place that records operations, with its own replay logic.

Who weighed in. Lane 1 proposed A. I agree. Recommendation: A. If you wait: nothing is blocked. Where: Program Design line 80, point (2), and the report on the existing automation-events list.

4. A Wake message that was mid-delivery when the move happened

The decision: where does the machine record a Wake delivery that started locally and finishes after central has taken over?

Background. If a Wake's message is being delivered into a session during the move, the delivery finishes on the machine. Central still has to know about it, or it would send that occurrence again: a double message. So during the freeze, the machine gives that delivery a central Firing ID. Central records it as "already with the machine", and the machine later reports the outcome under that ID, with a numbered report so central can apply reports in order. The question is where the machine keeps that ID and report number.

What changes

Two usually-empty columns, carried_firing_id and carried_report_seq, on the local delivery row that already represents this delivery.

Gains

One row owns the whole delivery and its report number.

Costs

Two columns in a migration.

What changes

Record it in firing_receipts, which requires a Batch ID.

Gains

The same table as other central work.

Costs

A carried delivery has no Batch, so it would need a fake Batch ID or a table rebuild. AGENTS.md warns against rebuilds.

Who weighed in. Lane 1 found that the receipt table can't hold it, and I chose A. Recommendation: A. If you wait: nothing is blocked. Where: Program Design line 79, "Handover import contract", and line 80, point (3).

5. Who sent the first message of a session created on another machine

The decision: when you create a session on B from A, with a first message, how does B record that the message came from you?

Background. From machine A you can create a session on machine B and give it a first message (Specification R16, line 142). Central checks that the request really comes from you on A. B then delivers the first message into the new session, and saves it as a message with an origin: who sent it. Today a saved message's origin can only be one of three things:

  • a session;
  • "owner, unverified";
  • the Router.

None of them means "this person, verified by central, from machine A". An agent's first message is fine: its origin is its session.

What changes

One new stored origin kind, HumanUser { installation }, used only by this central-verified path.

Gains

The message is correctly credited to you, on the machine you sent it from.

Costs

A new kind in saved message data. Existing rows don't change.

What changes

Nothing new is stored.

Gains

No data change.

Costs

It mislabels a message central did verify as unverified, and hides which machine sent it.

What changes

A person on another machine can't send a first message; only agents can.

Gains

No data change.

Costs

You couldn't create a remote session with a first message yourself, which your requirement includes.

Who weighed in. Lane 2 found that the stored origin can't express it, and proposed A. I agree. Recommendation: A. If you wait: nothing is blocked. Where: Program Design line 83, "Remote create first input on the target".

Approvals, in three steps

Approval state lives only in interaction.sqlite; the JSON files go. Routes, meaning who created a session and who answers its prompts, eventually move to central so prompts can reach an approver on any machine.

StepWhereWhat
1Database PRapproval-routes.json is imported once into a table in interaction.sqlite, then deleted. The old approval-history.json code and file are removed.
2Automations PRNamed interim step: a remote create with no approver gets the target machine's Chief of Staff session, which you name once per machine. A machine with none named refuses before creating anything.

Decided earlier

  • Automations are central definitions of message schedules, one list per organization; one organization for now.
  • Central fires on its own clock and batches per machine at send time (option A).
  • Cancel happens in central only; nothing chases a machine.
  • Machine-to-central reports go out every 500 ms or 100 items.
  • A 5-minute grid; no per-organization offset.
  • The limits live in the schema and in validation, so agents see them.
  • Cost measurement on staging waits until later.
  • Retention, vacuum and WAL on every database, with your retention table (PR 1).
