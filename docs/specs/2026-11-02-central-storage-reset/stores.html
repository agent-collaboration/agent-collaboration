Databases: one consolidated plan for both designs

Your rule is to consolidate, not to add. Neither design adds a database, and both put their new data into stores that already exist. Central goes from several object types to one Fleet store plus one store per project, which is D1. Each Router ends up with one store for its link to central, fleet.sqlite, instead of two databases and three kinds of JSON file. It goes from 10 files plus project files down to at most 8, through D3 and D4b, with further merges checked in D3. This page covers the central storage reset design (codex-router) and the Fleet access design (agent-vm). Both Leads agree to it (the Fleet access Lead concurred with corrections, all folded in).

No new database file and no new storage crate. New data goes in as tables in an existing store, with a prefix for its concern. Every table gets a UUIDv7 primary key, created_at and updated_at, typed columns, and CHECK constraints only for booleans. A store is a separate file only when there's a written reason, and “it was added that way” isn't one. Re-enrollment clears named tables, never whole files.

This morning I had agreed to a new fleet-client.sqlite for login, and Fleet access had already built a separate fleet.sqlite crate. Fleet access had also planned an Organization Registry store on central, per-organization authority objects and per-machine Connection presence. All of these are withdrawn in favour of tables in existing stores. I also found that the new enrollment reset deleted fleet-cache.sqlite as a whole file, which would have wiped the login tables. The Router lane is changing it in D1 to clear only the named cache tables.

Refused for now, with no queue and no redelivery, as a marked workaround until remote start is redesigned (owner, 2026-11-03: "make it clear in design it's a workaround, and in the code until redesign"). D2's Program Design follows this (d2-fleet-sends-and-remote-create.md).

What D3 still decides

For each “D3 checks” row, D3 either merges the store or writes down the reason it stays separate. The likely reasons are a different writer process (the two UI tools run separately from the Host) and a store that must survive while another one is being reset. Each D3 decision goes to both Leads and to you before code.
