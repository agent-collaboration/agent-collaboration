## Target and evidence rules

Observe the delivered branch's compiled iocraft components, with source revision and dirty diff recorded, at 120×36, 76×30, 48×24 and constrained 48×12. Exercise actual resize events between these sizes. Include long account/session names, both account providers, CJK/wide glyphs, long Details, unavailable/no-match choices and all current account classifications. Fixtures supply records and replace external effects; they do not replace the renderer, input dispatch, component state or layout. No production Router replacement, credential mutation, paid provider call or real reset is needed for a presentation change.

Use the existing mock-terminal render loop for deterministic keys, pointer events, geometry and styles. Its name contains “mock”, but the product's real component/input/layout code runs; only the terminal driver and external dependencies are substituted. It proves that boundary, not terminal font appearance or production service behavior. A compiled PTY/capture journey adds actual terminal presentation, original screenshot bytes and human inspection. Never reconstruct an image from plain-text frames and call it an app screenshot.

The project `verify-codex-router` skill currently covers Host/callback/Tailnet work and harness-report screenshots, not these lasting UI journeys. Its report screenshots are explicitly not native app proof. The paired Verifier must add a lasting TUI journey and its driver before relying on it. Existing `picker_capture_tests.rs` writes diagnostic text/SVG; that is useful diagnostic output, not the required screenshot. Ghostty computer-use access is denied; do not bypass that denial. The existing `compiled_compact_current_storyboard_exports_both_real_tuis` VHS/ttyd journey captures this task's compiled fixture process through its own PTY; it may be extended for these screens, clearly labeled as that target, without inspecting or controlling the denied Ghostty app. It is not Ghostty proof; a missing supported route remains an explicit proof gap.
