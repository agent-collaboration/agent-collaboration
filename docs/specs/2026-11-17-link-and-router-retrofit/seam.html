0 · Draft 4 (2026-11-18): what changed, and it governs where it differs below

These revisions answer the independent extra-high design review (findings 1, 2 and 4) and the owner's identity decisions of 2026-11-18.

  1. Identity (owner): one id, MachineId (UUIDv7, the Router install's id, in the Router database). The one address is SessionRef { machine_id, session_id }, with no endpoint. Caller::Session(SessionRef). SessionAddress, "installation", "peer" and "service id" are gone. Agents' tools take { type: "local", sessionId } or { type: "machine", machineId, sessionId }.
  2. Three status questions, three answers. Earlier drafts blurred them together.
    • request_status(caller, request), "what happened to MY request": the local outbox row if there is one (InOutbox, Sent, Answered(reply), Ended(reason)). If there's no local row, the Router asks central's request log (a caller-scoped replay read; central keeps 24 h), which answers Answered, Refused or NotFound. The read names its store: RequestStatusQuery { request_id, scope: Organization | Workspace(WorkspaceId) }. The scope comes from the original request (the outbox row's payload, or Uncertain { request, scope } for an immediate write). An unreadable outbox or an unreachable central answers StatusUnavailable, never NotFound. NotFound means no matching record for this caller in the selected store.
    • message_status(message_id), "what happened to a message I sent": central's ListQuery::MessageStatus (sender-scoped) → Queued | Delivered | Failed{reason} | Cancelled{reason}. It's renamed from "MessageDelivery", which already names the delivery mode.
    • Late outcomes arrive as DeliveryOutcome carrying sender_request_id, so a sender whose first reply was lost still matches the outcome to its request.
  3. Submit results are truthful. OutboxUnavailable only when nothing can have been stored, because the store failed before its transaction began. An insert error whose commit is unknown answers Uncertain { request }, and the agent reconciles with request_status.
  4. "Delivered" means durably in the recipient Router's inbox (owner 297: "it goes to b's inbox"; 112: "just trust and move on").
    • The recipient Router sends Ack(Accepted) when its inbox insert commits, not after it hands the message to the agent.
    • The handoff to the agent session is Router-local and runs from the inbox, retried until done. It's exactly-once per message id (the local push key is the message id). The real provider handoff and per-session receipts belong to the Router retrofit (PR 4 lane).
    • Ack(Refused{reason}) only for a permanent local refusal: the session id is unknown to this Router, or more than one endpoint matches it.
  5. Lost Acks.
    • On every Welcome, the recipient Router re-sends the Ack for every inbox row it accepted in the last 24 h, and central treats repeats as no-ops. So a lost post-write Ack is recovered at the next reconnect.
    • A late Accepted after a cancel becomes DeliveredAfterAll.
    • An Ack for a message not addressed to the connection's machine is ignored, with a typed, logged reason.
    • Both hosts' link handlers must receive Acks: the Cloudflare handler that closes the socket on an Ack is a defect to fix.
  6. Storage: the outbox, the inbox and the identity all live in machine_local.sqlite. Nothing is in provider_operations.sqlite.
  7. Outbox end: both outbox kinds end at 15 minutes (NotSentWithin15Minutes / NotConfirmedWithin15Minutes), and there's no 24 h outbox end (owner 11-18). Withdrawing an item is not in v1.

1 · The call

// central-link-client (Lead A). Async; one injected clock.
pub trait LinkCalls {
    // payload carries a caller-minted UUIDv7 RequestId on every write (already in the contract).
    async fn submit(&self, caller: Caller, payload: RequestPayload) -> Submission;
    // scoped to the caller's own requests: another session's id answers NotFound.
    async fn request_status(&self, caller: Caller, request: RequestId) -> RequestStatus;
}

pub enum Submission {
    Answered(ReplyPayload),         // immediate kinds: central's answer
    InOutbox(OutboxReceipt),        // outbox kinds: stored, sends on the next mark
    Refused(SubmitRefusal),         // nothing sent, nothing stored
    Uncertain { request: RequestId },// immediate writes: sent, answer lost; may have applied
    ReadAnswerLost,                 // reads only, no id: the frame left, the answer was lost; reading again is safe
}

pub struct OutboxReceipt {
    pub id: OutboxReceiptId,        // = the write's RequestId (UUIDv7)
    pub flush_at: SyncTime,         // the next 1-minute mark
}

pub enum RequestStatus {
    NotFound,
    InOutbox { flush_at: SyncTime },
    Sent,                           // flushed; central's answer not yet in
    Accepted(ReplyPayload),
    Refused(RefusalReason),
}

pub enum SubmitRefusal {
    CentralUnavailable,             // immediate kinds: nothing left the Mac
    OutboxUnavailable,              // outbox kinds: the local write failed; nothing stored
    RequestIdConflict,              // the same RequestId was submitted with different content
    NotEnrolled,
    InvalidRequest(ProtocolError),
}
  • Caller, RequestPayload and ReplyPayload already exist and are merged: workspace-model/src/request_contract.rs:43 (Caller::Session(SessionAddress), Caller::Person) and central-link-protocol/src/link_request.rs:45,75 (Workspace(WorkspaceRequest), Mail(CentralMailRequest)). The seam adds no new identity field. The session rides in caller, as the Router claims it today. Agent session tokens stay parked by the owner and are decided with him before Feature 2's authentication builds on them.
  • The kind of an operation picks its path; the caller doesn't choose.
  • Safe replay: the caller mints the write's RequestId (owner, 2026-11-13: "the caller mints a UUIDv7 request id"). Central keeps the first answer for 24 hours, so resubmitting the same id returns it and never applies twice. The same id with different content is refused as a conflict. Doors that take an itemId/operationId pass it through as the RequestId.
  • Uncertain means the frame left the Mac and the answer was lost. The agent reconciles with request_status, or resubmits the same id. It never retries blind with a new id. CentralUnavailable is used only when nothing left the Mac.

3 · Receipts and what the agent sees

  • An outbox write returns InOutbox at once with a short receipt. The agent sees "in outbox" (owner: "'in outbox' is fine").
  • The agent's own reads show its unsent posts and messages marked "in outbox" (owner: "show as pending or in outbox").
  • Outcomes come back batched, one compact receipt per session per flush. Only accepted counts and refusals with reasons are pushed (owner: "batched by session and token-efficient"; "outcomes and problems only").
  • Outcome pushes reach the session through the Router's existing per-session delivery, arriving like any notice in the session's inbox. There is no separate stream.
  • Any receipt can be pulled with request_status, exposed as an MCP/API status request (owner: "able to pull the status with a request … in the api of the mcp").
  • The wording of receipts, "in outbox" and refusals belongs to the CLI+MCP Lead, in the same style as the session refusals: the state plus valid next steps, with short successes.

4 · When central is unreachable

  • Outbox kinds: they stay in the outbox and send after reconnect. That's what the outbox is for (owner 11-15: "covers network drops").
  • Immediate kinds: Refused(CentralUnavailable) at once. Nothing is queued, so a command never runs late without the agent knowing. Lead A's call, recorded.
  • Outbox expiry: see section 0, item 7.
