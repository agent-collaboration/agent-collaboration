# Provider-native capabilities in the installed Codex client (J1-J4)

Use this journey when Router changes how Codex discovers or selects a provider's own skills, plugins or commands, or how that history replays. Qualify each provider and journey on the declared candidate. Keep successful observations, failed attempts and unobserved outcomes separate; discovery alone does not establish native execution or history preservation.

Adopted outcomes: `docs/specs/2026-10-23-provider-native-capabilities/` Requirements U1-U7, Specification R1-R9 and C1-C5, and Verification Design rows J1-J4. Expected values come from those documents and from the controlled fixture, never from what the candidate shows today. A provider or version that can't supply an experience is reported as `explicitUnsupported`, `noNativeReference` or a named limit, never as a pass.

## Route and what stays real

Installed Codex `--remote unix://<endpointSocket> --cd <fixture worktree> -c features.mentions_v2=false resume <SessionId>` reaches the candidate Host, which forwards to the installed native provider. The per-invocation `mentions_v2=false` is the D1 reference launch: it puts skills and plugins under `$` and makes `@` file-only.

`scripts/verification/native-capabilities.sh --help` runs the Rust example `crates/codex-router-host/examples/verify-provider-native-capabilities.rs`; its modules live in `examples/provider_native_capability_verification/`. It drives the real client in a private pseudo-terminal and reads back through the endpoint socket, bounded public `events observe`, read-only Router operation rows, and the provider's own export and files. It never starts, stops or replaces a Router or Host, never creates Sessions, logs in or edits installations, and signals only its own client child.

Codex 0.163 builds plugin `Mention` items only from a picker binding (`input_submission.rs:343-365` in the task's exact-source snapshot), so the driver types `$` and part of the name, waits for the picker row, and selects with Tab (`chat_composer.rs:2228-2250`). The client's own session recorder (`CODEX_TUI_RECORD_SESSION=1`, `CODEX_TUI_SESSION_LOG_PATH`, set per drive) logs each outbound `UserTurn` before dispatch (`app/thread_routing.rs:533`, `session_log.rs:251-261`). Those items reach `turn/start` unchanged (`app_server_session.rs:1449-1460`), so the oracle checks the structured selection the real client sent.

## Prerequisites (Lead-operated)

1. **Fixture worktree.** The Lead creates a genuine detached linked Git worktree at the declared candidate HEAD in the run's owned evidence path, using the ordinary `git worktree` command (no fake `.git` pointer, no branch rewrite). Codex trusts it only by inheriting the main repository's existing trusted entry through a verified worktree registration (`crates/codex-native-integration/src/codex_project_trust.rs` `main_repository_root`, `project_trust`). No global trust is ever saved. Then materialize:

   ```sh
   scripts/verification/native-capabilities.sh materialize \
     --workspace "$EVIDENCE/workspace" --empty-workspace "$EVIDENCE/empty-workspace" \
     --record "$EVIDENCE/fixture.json"
   ```

   It refuses anything but a clean genuine linked worktree rooted at `--workspace`, outside the home directory, and only adds new files (create-new, never overwrite): two `SKILL.md` files under `.claude/skills/` and `README.verification.txt`. The empty comparison directory is created fresh beside it, never inside it. Templates live in `scripts/verification/fixtures/provider_native_capabilities/`. Each materialized skill gets a fresh canary that appears nowhere else. `router-native-arguments` replies `CANARY::<arguments>`; `router-native-second` exists only to build rejected multi-skill selections. The record keeps the worktree's HEAD.
2. **Candidate.** The Lead builds the three normal binaries into the owned build target, signs each through the repository runner, and starts the Router and Host through the ordinary `codex-router serve`/`host` lifetimes on a private root, with the fixture worktree as provider workspace. Record each process's PID, real UID, group, `lstart` birth and executable before any drive. Optionally record its owned closure with `processes capture --root-pid PID --output FILE` and check it after the Lead stops it with `processes check --inventory FILE` (observe only; it never signals).
3. **Sessions.** Create each Session through the installed Codex TUI's own new-thread flow against the candidate endpoint, with the fixture worktree as cwd, so the client owns it normally. No Agent-created Session, manufactured Human identity or relaxed settings authorization. Choose the model explicitly when the Session is created, from the models the Session advertises, then read the native setting back from the Session before any input and record the model actually used. A `/model` choice made only in the client and lost by quitting before a turn is client state, not native setup proof. A positive body-execution claim needs a fresh Session whose history holds no fixture canary; the driver checks the pre-run public observation and refuses otherwise. Use one fresh Session for J3 and another for J2 `leading` (which J2's rejection cases and J4 then share). One plan names one Session.
4. **Plan.** Write a `NativeCapabilitiesPlan` (`verification_models.rs`, camelCase, unknown fields rejected): `repository`, `sourceHead`, `binaries.{codexRouter,agentCollaboration,agentSessions}.{path,sha256}`, `binaryQualification` (the build's own record: one entry per target with `path`, `sha256` and empty `testGuardFeatures`), `routerRoot` (canonical), `endpointSocket` (mandatory: the endpoint socket the Host actually serves and the client connects to, as spelled at launch; a short alias such as `/tmp/...` of the canonical `/private/tmp/...` keeps it under the Unix socket path limit, about 104 bytes on macOS), `routerPort`, `expectedVersion`, `routerProcess` and `hostProcess` (`pid`, `realUid`, `group`, `birth`, `executable`), `codexCli`, `nativeExecutable`, `hostSearchPath` (the PATH the Host was launched with; required for `claude-local`), `acpAdapter` (`claude-local`: the package-declared CLI entry the Host actually runs, with its hash. For `@agentclientprotocol/claude-agent-acp` 0.81.2 that is the npx cache's `dist/index.js`: `package.json` `bin` and `scripts.start` select it, and it imports the implementation module `./acp-agent.js` and calls `runAcp`. The implementation module's hash may be kept as a separate fact but never stands in for the CLI entry. A same-version global copy differs), `endpointId`, `sessionId`, `queueObserver` (the verifier's own agent Session as `{"kind":"session","session":<SessionRef>}`, presented as the ACP actor for read-only queue observation; no Human identity is accepted), `fixture`, and the provider's own roots: `nativeHomeSkillRoots` (absolute), `nativeWorkspaceSkillDirs` and `nativeWorkspaceCommandDirs` (relative to the provider's project root), `nativeHomeCommandRoots`, and `nativeProjectRootMarker` (Cursor: `.git`, nearest ancestor, falling back to the cwd itself; omit when the cwd is the root). Take roots from the provider's native loader source and record the anchors in the run notes; never declare fixture-only roots or infer them from the candidate's answer.

## Qualification

Every journey qualifies before any drive and fails closed. Requirements:
- The Router root is canonical as declared, private to this user and not the production root.
- `endpointSocket` is absolute and is itself a Unix socket (not a regular file or symlink) named `<endpointId>.sock`. Its directory is canonically `<routerRoot>/agent-communication/router-sessions`, it is owned by this user and it is private. That one path is used for the installed client and the consumer requests; nothing rewrites it.
- The source is the declared clean commit.
- Each binary is in the build record as a normal build, matches its hash and has a strict debug signature (`dev.shravansunder.<binary>.debug`, team `974QD84WVC`).
- The installed Codex and native executable hashes match.
- For `claude-local`, the declared executable equals the global Claude that the Host's launch PATH selects. The verifier mirrors `global_claude_executable.rs`: package and transient directories and SDK binaries are excluded, and a normal global package symlink stays eligible.
- The Router and Host are live with their recorded identity and real UID (ps `ruid`; a setuid descendant raises only the effective `uid`). The permanent live setuid control runs only on macOS: `/usr/bin/top` is setuid root there, and `-l` is a macOS flag. On Linux CI the parsed setuid and foreign-owner cases and the live PID 1 foreign-owner case still run.
- For `claude-local`, the declared ACP adapter matches its hash and a live Host descendant runs from its install root (the parent of its innermost `node_modules`). Only that PID and root are recorded; argument lines are not kept.
- The health version and `service.json` match.
- The fixture worktree is still at the declared commit with its recorded canaries.

Additional worktree changes are recorded in `qualification.json`.

Each client drive watches the ready composer for five more seconds before the first keystroke. Codex 0.163 draws the saved folder-trust dialog ("Trust this folder? … Your trust decision will be saved") *after* the composer, so a composer alone proves nothing. A trust dialog fails the drive, and the driver refuses all input once it appears, so it never answers one.

## Drive order and distinct arguments

J3 runs first on its own fresh Session. J2 `leading` runs first on a second fresh Session; the rejection cases, then J4, follow on that same Session. Shared-Session repeats are useful controls and history, never independent body proof. Give each model-bearing drive its own arguments, so each history entry and reply is unique. Include a literal `$`, non-ASCII text and a newline where the case allows (the driver pastes multi-line text with bracketed paste).

## Evidence and cleanup

Each run keeps these files in its fresh private directory:
- `binding.json`, `qualification.json` and `fixture.json`;
- the raw consumer replies, observations and operation rows;
- native plugin rows or facts (allow-listed fields only);
- the `.pty` captures and the client recorder `.session.jsonl`;
- one `{label}-cleanup.json` per drive;
- `result.json`.

Keep these under the task's private evidence home, not in this skill.

Each cleanup record states:
- whether a trust dialog appeared;
- whether the capture is complete;
- whether the client quit through Ctrl-C or was force-stopped (only its own child);
- every descendant acquired through it by real UID;
- which of those remained (none may);
- the global Codex config digests before and after, and one of three states for the unchanged-preferences claim (R5):
  - `provenUnchanged`: both readable and equal. Only this closes R5.
  - `changedUnattributed`: both readable but different. A changed digest does not identify a writer, so R5 stays UNKNOWN.
  - `unobservable`: a file exists but cannot be read. That is never treated as absence, and R5 stays UNKNOWN.

A config state never stops or skips a feature case and is never a product failure on its own; only an actual attributable unauthorized write by this run fails. Absence is reported only when the file does not exist. The Lead stops the Router and Host through their ordinary lifetimes and confirms the evidence survives. The fixture worktree and empty directory are run residue beside the evidence.

## Open items and limits

- **Provider coverage:** exercise the client recorder, composer readiness (`›` plus the trust watch), picker rows, cursor-position reply, client-error words and trusted fixture worktree on the declared candidate. Record native execution, command replacement and canonical history separately; a successful local handler does not establish model prose or a skill-body effect.
- **R5 unchanged preferences** is closed only by `provenUnchanged` on every drive. Any `changedUnattributed` or `unobservable` drive leaves it UNKNOWN for the run, while the feature cases still count separately.
- **Claude native skill roots:** qualify the composed native loader for the installed version, including user, legacy command and installed-plugin roots. Advertising the fixture confirms only `.claude/skills`.
- **Per-skill enablement** inside a plugin is unqualified: native overrides exist and package enablement is not a stand-in, so it is not asserted. Settings-file disabled overrides are likewise unverified.
- **Plugins:** selection stays explicitly unsupported until a native intent route and prepared-context observation are qualified (G2). Plugin rows prove discovery only. Cursor has no qualified native plugin export, so its plugin leg is `noNativeReference` or `explicitUnsupported`.
- **Native operation counters** don't exist for the installed providers; Router operation rows and public events are reported as Router evidence (G3).
- Per-kind Partial/NotObserved plugin detail variants belong to the permanent product tests. Hook events compare by name, ignoring case and separators; the semantic `HookEventName` mapping is not judged here.
- **Cursor:** native roots anchor at the nearest `.git` project root, unchanged by `--disable-project-configs`, falling back to the cwd itself (Lead source reads of the installed loader). Its disabled fact is the loader's `user-invocable` skip. Other per-skill settings stay unverified.
