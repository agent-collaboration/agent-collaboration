# Provider-native capabilities in the installed Codex client (J1-J4)

Use this journey when Router changes how Codex discovers or selects a provider's own skills, plugins or commands, or how that history replays. It is **draft**: the driver and its oracles have passed their apparatus tests, but no run has happened on a real candidate yet. Every open item below stays open until a run closes it.

Adopted outcomes: `docs/specs/2026-10-23-provider-native-capabilities/` Requirements U1-U7, Specification R1-R9 and C1-C5, and Verification Design rows J1-J4. Expected values come from those documents and from the controlled fixture, never from what the candidate shows today. A provider or version that can't supply an experience is reported as `explicitUnsupported` or as a named limit, never as a pass.

## Route and what stays real

Installed Codex `--remote unix://<router_root>/agent-communication/router-sessions/<endpoint>.sock --cd <fixture workspace> -c features.mentions_v2=false resume <SessionId>` reaches the candidate Host, which forwards to the installed native provider. The per-invocation `mentions_v2=false` is the D1 reference launch: it puts skills and plugins under `$` and makes `@` file-only. Global Codex config is hashed before and after every drive and must not change.

`scripts/verification/native_capabilities.py --help` is the scheduled entry point. It drives the real client in a private pseudo-terminal and reads back through the endpoint socket, public `events observe`, read-only Router operation rows, and the provider's own export and files. It never creates Sessions, logs in, edits installations or stops a Host.

Codex 0.163 builds plugin `Mention` items only from a picker binding (`input_submission.rs:343-365` in the task's exact-source snapshot), so the driver types `$`, waits for the picker row, and selects with Tab (`chat_composer.rs:2228-2250`). The client's own session recorder (`CODEX_TUI_RECORD_SESSION=1`, `CODEX_TUI_SESSION_LOG_PATH`, set per drive) logs each outbound `UserTurn` before dispatch (`app/thread_routing.rs:533`, `session_log.rs:251-261`). Those items reach `turn/start` unchanged (`app_server_session.rs:1449-1460`), so the oracle checks the structured selection the real client sent.

## Prerequisites

The owned runtime creates that directory with `exist_ok`, and the native providers start with it as their workspace, so they see the fixture from startup. Put the empty comparison workspace beside it. Both stay outside the home directory:

   ```sh
   uv run --offline --no-project --with pydantic==2.14.1 --with websockets==17.3 --python 3.13 \
     python -m scripts.verification.native_capabilities materialize \
     --workspace "$EVIDENCE/workspace" --empty-workspace "$EVIDENCE/empty-workspace" \
     --record "$EVIDENCE/fixture.json"
   ```

   Templates live in `scripts/verification/fixtures/provider_native_capabilities/`. Each materialized `SKILL.md` gets a fresh canary that appears nowhere else. `router-native-arguments` replies `CANARY::<arguments>`; `router-native-second` exists only to build rejected multi-skill selections.
2. Launch the candidate with the owned runtime described in `SKILL.md` (normal signed binaries, standard Host A) and pass `owned_runtime.py --check`. The journey requalifies through the same functions (`qualify_normal_binaries`, `verify_ready`, `qualify_global_claude`) and the started Host's recorded identity. It fails before any drive if the source is dirty, a signature or hash differs, the Host phase was settled, or the Claude binding changed since launch.
3. The Lead (or the run's declared operator) creates one synthetic Session with the candidate's `agent-collaboration`: `conversation create --endpoint claude-local --access write-restricted --cwd "$EVIDENCE/workspace" --approver '<Lead SessionRef JSON>' --service-directory <router_root>/agent-communication`. The approver is the explicit agent SessionRef declared for this run, never a Human or owner identity assumed on someone's behalf. Use the owner-required test model (`claude-haiku-5-5`) only after `session inspect` shows it is advertised. Keep the returned SessionRef and operation ID. The driver never creates Sessions.
4. The roots describe the provider's real setup, including its ordinary user skills and installed-plugin skill directories. Never declare fixture-only roots to avoid the installed setup. ## Drive order and distinct arguments

One Session carries every drive. Give each model-bearing drive its own arguments, so each history entry and reply is unique. Include a literal `$`, non-ASCII text and a newline where the case allows (the driver pastes multi-line text with bracketed paste).

| Step | Command | Proves | A wrong build that fails |
| --- | --- | --- | --- |
| J1 | `catalogue PLAN --output DIR` | `skills/list` returns the fixture with its real file origin, repo scope and enablement. Every row lies under the provider's own roots, so a shared root such as `~/.codex/skills` passes only when the provider's loader reads it. Every enabled row is advertised by the bound provider under the namespace its file implies: a skill inside an installed plugin's directory needs `<plugin>:<skill>` for that plugin, and another plugin's same-named skill doesn't count. A disabled row is a real skipped file, and its own frontmatter must carry a declared native disabled fact. A row merely marked `enabled=false` fails, a natively skipped file reported enabled fails, and a disabled file never stands in for an advertised active definition of its name. A `skills/list` error must name an actual native skill source (a `SKILL.md` or its directory under the provider's roots); a package directory, a marketplace manifest or any other path is the wrong role. An empty workspace borrows nothing. One enabled, really installed plugin's own skill file also appears by path with the plugin's enablement (a discovery sample beside the fixture; nothing executes, and having no such plugin is a setup gap). `plugin/list` and `plugin/read` match the provider's own plugin export and plugin files item by item. Marketplace rows and load errors may name only the actual manifest from `claude plugin marketplace list --json` (`installLocation/.claude-plugin/marketplace.json`, present on disk), and an omitted plugin is excused only by its own marketplace's manifest error. `plugin/install` is rejected with no native change. The `$` picker shows the fixture; `@` shows a workspace file. | A substituted Codex catalogue, a fake or `builtin` path, a borrowed workspace, an omitted plugin excused by an unrelated error, a manufactured remote identity, invented detail items, accepted management |
| J3 | `commands PLAN --arguments A --output DIR` | Successive `available_commands_update` Notices, with the latest as current (replacement is `observed` only when a name disappears). `conversation prompt "/router-native-arguments A"` produces `CANARY::A` from exactly one Router prompt. Installed Codex refuses `/router-native-arguments` locally, with no Router operation. | A mangled command or argument, a reply without the body-only canary, refusal counted as invocation |
| J2 | `select PLAN --case leading --arguments B --output DIR` | The client sent one Text plus a Skill with the fixture's real path. One prompt reached `CANARY::B`. | A dropped selection, a body copy, the wrong skill, corrupted arguments |
| J2 | `select … --case nonleading`, `two-skills`, `selected-steer` (fresh arguments each) | Each case is explicitly rejected: the client shows an error, no prompt or turn is added, and no canary appears. Steer allows only its ordinary `STEER_BASE_OK` turn. | A silent drop, a native submission, auto-queue |
| J4 | `history PLAN --arguments B --ordinary-live-capture <steer DIR>/select-selected-steer.pty --output DIR` | `thread/read` and `thread/resume` show `/router-native-arguments B` (outer whitespace may be trimmed) and `CANARY::B` once each. Pure display adds no Router operation or turn. The unchanged `acp_metadata_observation.check_metadata_observation` passes on the same Session, with the steer turn as the genuine-prose control. | Changed or missing history, replay-driven prompts, metadata leaking into prose or deleted |

Add `--unloaded-resume` to J4 only after an explicit unload such as a Host A→B reopen; it then allows the existing load, never a prompt.

Public observations stay within the CLI's parser bounds (`event_commands.rs:49-79`: at most 4096 events and 1 MiB per call, and `--after-sequence` only with `--epoch`). The driver follows `resultLimitReached` pages with the observed epoch, as the client's own follower does. An epoch change, a resync, a disconnect or an unbounded page run fails the observation rather than counting as complete.

A run exits 1 when an oracle rejects the evidence or the run breaks; read `DIR/failure.txt`. A selected-steer case that reports a harness race ran as a fresh turn, not a steer. Rerun it; it is neither pass nor fail.

Keep these under the task's private evidence home, not in this skill.

## Open items and limits

- **Draft:** no drive on a real candidate yet. The client recorder, the PTY readiness pattern (`›`), the picker rows, the cursor-position reply and the client-error pattern all await their first real run.
- **Claude native skill roots** are not source-qualified yet. They wait on the composed native loader source, including user and installed-plugin roots. The fixture's own `.claude/skills` is confirmed only by Claude advertising the fixture, and the candidate's answer never stands in for that source.
- **Per-skill enablement** is unqualified here. Native per-skill overrides (user-invocable, configured state) exist, and package enablement is not a stand-in, so neither the installed sample nor plugin detail asserts skill `enabled`. That stays a named gap until native skill facts are qualified.
- **Plugin namespaces** come from the provider's own export id (`<name>@<marketplace>`). That this equals the advertised namespace is confirmed per run only by the advertisement check passing on real rows.
- **Plugins:** selection stays explicitly unsupported until a native intent route and prepared-context observation are qualified (Lead disposition G2). Plugin rows prove discovery only. Cursor has no qualified native plugin export, so its plugin leg is recorded as `noNativeReference` or `explicitUnsupported`.
- **Native operation counters** don't exist for the installed providers. Router operation rows and public events are reported as Router evidence (G3).
- Per-kind Partial/NotObserved plugin detail variants belong to the permanent product tests. This journey observes real installed plugins as they are. Hook events compare by name, ignoring case and separators; whether the semantic mapping to `HookEventName` is correct is not judged here.
- **Cursor:** draft. Its native skill roots are anchored at the nearest `.git` project root, unchanged by the owned runtime's `--disable-project-configs` (Lead source recheck of the installed `index.js` config loader and `7096.index.js` `getProjectRoot`/`loadCommandsAndSkills`). With no `.git` ancestor, the native finder falls back to the cwd itself (installed `utils/git.ts` `f()` returns its input, Lead source read). The oracle uses that same fallback, so a marker-free owned workspace is its own root and needs no fixture change. Cursor's disabled-row fact is the loader's `user-invocable: false` skip (`native_disabled_markers`). Other per-skill settings and identity cases stay unverified until qualified.
